PolyTM: learning polynomial-time oracles

Created on July 08, 2025

2025   ·   rl   algorithms   ·   research

PolyTM is a reinforcement learning environment I built inside PufferLib, around one question: can a neural network learn to discover algorithms? Not to answer a problem instance, but to produce the procedure that answers every instance, and to do it in polynomial time.

The idea

The environment is a machine. There is a tape of integers holding the problem, and the agent does not output answers, it outputs instructions: pick two cells, pick an operation, add or multiply, pick a cell to write the result into. Step by step it edits the tape, and when it halts, the reward depends on whether the designated result cells hold the right values. The network is not being trained to know the answer. It is being trained to build the computation that produces the answer.

The environment also keeps the two honest ledgers of computation: how many steps an episode took and how many cells it wrote. Running time and space, logged for every episode, because an algorithm that exists but wastes the tape is not the algorithm we are looking for.

The committed version is this register machine. The version it was growing into is a proper multi-tape Turing machine, separate work, state, and result tapes, read heads with observation windows, an alphabet, penalties for refusing to halt. Same idea, stricter machine. The heads and their windows exist for a blunt reason, the observation vector cannot be the whole tape once the tape grows, so the agent reads through small windows around its heads and has to learn to move them, which is, of course, exactly what a Turing machine does. We experimented along that axis, more heads with narrow views against fewer heads with wider ones, because visibility was the budget everything else had to fit inside.

The tasks across versions ran from summing and binary addition to sorting, each instance random every episode. A Sudoku solver was planned as the showpiece and never came through.

The policy that drives it is a transformer over the tape. Each integer cell is read as its bytes, its sign, and a hashed identity, embedded and attended over, with an LSTM carrying memory across steps, trained with PufferLib 3.0’s PPO. The one thing this setup refuses to do is memorize instances: the problems are random every episode, so the only thing worth learning is the procedure.

Where it came from

The question came out of algorithms, not machine learning. Working with Dr. Pallavi Jain on ranked aggregation, the open problem in the air was EFX, whether an envy-free-up-to-any-good allocation always exists, known for three agents and open from four onward, and she encouraged me to hunt for a counterexample. Hunting for counterexamples and hunting for algorithms are the same kind of search, discrete, enormous, and allergic to gradients, and I wanted to know whether a learned searcher could walk spaces like that. The first version of the environment says so outright. Before the general tape machine there was poly_time, and its problem was literally a fair-division instance, four agents, a random utility matrix over the items, and the machine’s output was an allocation with a halt flag. PolyTM was what it generalized into, the small, controlled version of the question.

It did work, for some of it. The network learned to compose correct computations for the arithmetic tasks, and the work pushed further from there. What it did not give me is the thing I wanted next: you can watch the tape and see that it computes, but not read back what algorithm it found. Explainability was the planned second half, extracting the discovered procedure from the trained policy, and it stayed planned.

Edit: I did not see it at the time, but this was an early run at the idea I now work on. A model that, given a task, produces the computation that solves it rather than grinding out the answer itself, that is the whole shape of my current work on meta-reasoning in language models. PolyTM was the same bet, placed on a tape instead of a trajectory.
