New Beginnings

by Anshul Thakur

24 min read

This week, I reviewed the benchmarks, did a literature review, and conceptualized the “target”.

Literature Review

“Code generation” is a broad and well-researched area. The literature spans code generation in both modern and earlier foundation models; domain-specific applications such as quantum computing, visual CAD, and robotics; methods for collecting and synthesizing training data; and post-training approaches for code-generation tasks. I had to skim more than 2000 representative papers in this area. I’ll describe the main strands of this literature that are relevant to our problem’s motivation.

Modern code LLMs

Modern LLMs are trained extensively on code generation because code generation not only supports reasoning, but pretraining on high-reasoning code-gen and maths artifacts and post-training on code-generation and maths tasks help develop the models’ overall reasoning abilities.[1]

MiMo and MiMo-V2-Flash

MiMo is Xiaomi’s 7B reasoning model, and what stood out to me is that they build reasoning from pretraining itself rather than adding it at the end. They re-extracted maths and code from the web, mixed in synthetic reasoning data (which, interestingly, they could train on for many epochs without overfitting[2]), and pretrained on 25T tokens with multi-token prediction.[3]

For RL, they used about 130K verifiable maths and code problems with a modified GRPO: no KL loss, dropping prompts where every sample passes or fails, and a higher upper clip to keep the policy exploring. For code, instead of rewarding only full passes, they grade tests by difficulty and give partial credit the way IOI scores subtasks, so even hard problems teach something.

MiMo-V2-Flash scales this to a 309B MoE (15B active) trained on 27T tokens, with mostly sliding-window attention to keep long context cheap. Its post-training adds domain teachers, each trained with RL, that give token-level feedback on the student’s own outputs, plus agentic RL on more than 100K real GitHub issues checked by unit tests. It reached 73.4% on SWE-Bench Verified, the best open model at the time of release.[4]

Instruction-tuning data synthesis

The instruction-tuning phase had a problem: it was hard to get good instruction-tuning samples; most human-written samples were biased, and LLM-generated samples couldn’t scale in difficulty.

Older solutions to problem generation start with a “seed” and use different techniques to generate a <problem, solution> pair, or generate instructions from the seed and use a teacher model to generate solutions or harden/evolve the generated instructions.[5]

This is followed by filtering the samples: simple de-duplication or n-gram de-dup, filtering out wrong samples, and filtering out easy samples by sampling solutions from the student LLM and using LLMs as judges.

Note that wrong samples can also be used for training, so they are not entirely wasted.

Code Evol-Instruct fixed this by evolving the data: they started with a dataset of 20K coding tasks, asked an LLM to make each one a bit harder (add constraints, add reasoning steps, add buggy code as misdirection, demand better time or space complexity) and to answer it, then repeated the process, merging every round into the fine-tuning set. Three rounds (about 78K samples) worked best; a fourth lowered the benchmark score.

Although we now have much more high-quality instruction-tuning data for code generation[6], it still helps to study modern data-generating techniques.

The newest problem generators sample from an explicit structure instead of rewriting seed tasks. EpiCoder has an LLM extract a forest of code features from raw files, then samples subtrees by feature frequency, with subtree size setting difficulty. SciWalker random-walks a graph of scientific API operators instead.

In these modern approaches, rather than model writing code plus its own tests (KodCode), the approach splits tests: an LLM-written generator produces inputs, and a validator checks them against the program. Outputs are a majority vote over many sampled solutions, since wrong ones disagree. X-Coder votes over 8 solutions from several models, picks the best on half the tests, and confirms it on the other half. With rich tests, keeping 60 to 80% passes beats demanding 100%.

Once solutions are verified, selection mostly comes down to coverage. At a fixed budget, more distinct tasks with one solution each beat fewer tasks with several, and picking tasks that make the teacher reason longer beats difficulty ratings.

Due to the availability of large teacher models, we can now easily sample high-quality instruction-tuning samples, and in MiMo and MiMo-V2-Flash they use a technique where they sample rollouts for input prefixes and remove those for which the pretrained model consistently passes all test cases and post-train on the rest.

AlphaEvolve

AlphaEvolve is a code improvement (evolution) pipeline for problems with machine-gradable outcomes.

It takes a problem description prompt, starting code, and a scoring program, and evolves the starting code into a high-scoring evolved program.

AlphaEvolve keeps a database of programs and their scores. It samples one program as the parent and includes it in the prompt, along with a few other programs and their scores as inspiration. Gemini Flash or Pro then proposes code changes using SEARCH/REPLACE blocks. A worker applies these edits, then checks, runs, and scores the resulting program. The system adds promising candidates back to the database, and the process repeats. The database draws on MAP-Elites and island-based populations to keep both strong programs and different approaches.

In the paper’s results, AlphaEvolve found a way to multiply two 4 × 4 complex-valued matrices using 48 scalar multiplications instead of Strassen’s 49. It also improved Google’s job scheduling, recovering an average of 0.7% of computing resources that would otherwise go unused. Another improvement to matrix multiplication code reduced Gemini’s overall training time by 1%.

AdaEvolve

AdaEvolve is a code-improvement pipeline that changes its search strategy depending on whether its programs are improving. Like AlphaEvolve, it takes a problem description, starting code, and an evaluator. It also takes a model and a limit on the number of attempts, and returns the best program it finds.

It keeps several separate groups of programs, called islands. Each attempt chooses a group, samples a parent and some other programs as examples, and asks the model to produce a new version. The evaluator runs the new code, and the system tracks recent improvements to the group’s best score. The groups occasionally share their best programs.

Within a group, it chooses between refining strong programs and exploring different approaches. When exploring, each program has an equal chance of being the parent, and the prompt asks for a different approach. If progress stalls, exploration becomes more likely; it does not replace refinement entirely. In the reported settings, the chance of exploration ranges from 10% to 70%.

Group selection is a separate decision. AdaEvolve combines recent improvement with a bonus for groups that have received fewer attempts. This gives productive groups more attention without ignoring less-tried ones. It does not simply switch to choosing all groups equally when they stall.

When progress stalls across all groups, two separate rules can trigger: starting another group and asking for new approaches. A new group starts from a randomly sampled existing program in the archive. The old groups remain; they are not split or discarded.

To suggest new approaches, the model gets the problem, evaluator, best program and score, and previously tried approaches with their outcomes. Its suggestions go into later code-generation prompts, including those for existing groups. A new approach can therefore revive an old group if the resulting code improves its best score, making refinement more likely again. Starting a new group alone does not guarantee a different approach or an escape from the same dead end.

In the paper’s comparison on 172 Frontier-CS algorithm and systems problems, AdaEvolve achieved an average score of 61.33, compared with 47.79 for ShinkaEvolve and 50.75 for OpenEvolve. All three used GPT-5 with a budget of 50 model calls per problem. These are benchmark scores, not percentages of problems solved; equal call counts also don’t necessarily mean equal cost or runtime.

ACE / RepoZero

RepoZero is a benchmark for generating a code repository from scratch that behaves like an existing one. ACE (Agentic Code-Test Evolution) is the coding and testing process proposed in the same paper to improve these generated repositories.

The input includes a description of the required APIs, four example tests with expected outputs, and the target language. The agent must build the replacement without seeing the source code. RepoZero contains 400 Python-to-JavaScript tasks and 200 C/C++-to-Rust tasks.

ACE starts with a coding agent that writes the repository. A separate testing agent generates test inputs and runs them through the original program to get the correct outputs. It then tests the new code on the same inputs. If the outputs differ or the code fails, the errors go back to the coding agent, which edits the code and tries again in a loop.

The loop stops when the generated tests pass, or the allowed retries are used up. The final code is checked on separate hidden tests.

In the paper’s Python-to-JavaScript experiments with DeepSeek V3.1, two rounds of testing and revision increased the task pass rate from 26.08% to 42.88% with OpenHands-bash, and from 43.76% to 52.06% with Mini-SWE-Agent. These percentages reflect the share of benchmark tasks that passed all tests.

The updated benchmark paper also reports Claude Sonnet 4.6 with Mini-SWE-Agent passing 54.70% of Python-to-JavaScript tasks and 47.58% of C/C++-to-Rust tasks. These are separate model-and-agent results, not the ACE experiment above.

ViperGPT

ViperGPT is a framework that answers visual queries by writing a Python program that calls vision models. It takes an image or video and a natural-language query, then returns the answer by running the program.

The model (Codex) is given an API, not the implementations: an ImagePatch class with methods such as find, exists, verify_property, compute_depth, simple_query, and llm_query, each with its signature and a docstring, plus a few example query and code pairs. It writes one Python function for the query. Each method is backed by a pretrained model: GLIP for finding objects, X-VLM for checking attributes, MiDaS for depth, BLIP-2 for simple questions about a patch, and GPT-3 for world knowledge. Python handles counting, comparing, sorting, loops, and conditions.

Nothing is trained. Because the program is plain Python, every intermediate value can be inspected, and a module can be swapped for a better one without touching the program generator.

In the paper’s results, ViperGPT scored 48.1% on GQA and 51.9% on OK-VQA, the best zero-shot numbers listed (BLIP-2 scored 44.7% and Flamingo 50.6%), 72.0 IoU on RefCOCO against 58.6 for the best zero-shot baseline, and 60.0% on the NExT-QA video benchmark, where it beat the supervised models on the hard causal split (56.4% against 47.8%). Zero-shot here means no training on the task; the vision models inside were trained, just not on these benchmarks.

VISPROG is the same idea from a few months earlier, with its own small program language instead of Python: GPT-3 writes one module call per line, with names like Select, ColorPop and Replace, from in-context examples, and the modules cover detection, question answering, image editing and Python expressions. On GQA, it scored 50.5% against 47.8% for the question-answering model used on its own, and on NLVRv2, 62.4% without ever training on image pairs, where a model fine-tuned on them scores 76.3%.

ADAS

ADAS (Automated Design of Agentic Systems) is a search where a model writes whole agents as code. Its algorithm, Meta Agent Search, takes a task description, a validation set, and a small framework with functions for calling models and formatting prompts, and returns the best agent found.

An agent is one Python forward function. It takes the task input and returns the answer, and inside it can call the model any number of times, with any prompts, roles, loops, voting, or self-checks. Since the language is general, any agent design can in principle be written this way.

The search keeps an archive of agents and their scores, optionally started with hand-designed ones such as Chain-of-Thought and Self-Refine. In each iteration, the meta agent (GPT-4) reads the archive, writes a description of a new idea and its code, checks its own design twice for novelty, and runs the new agent on the validation set. If the code fails, the meta agent fixes it, up to five times. The agent and its score go into the archive, and the loop repeats 25 to 30 times in the paper. There is no population or selection step; the whole archive is in the prompt, and the meta agent decides what to build on.

In the paper’s results, with discovered agents run on GPT-3.5, Meta Agent Search scored 79.4 F1 on DROP, 53.4% on MGSM, 69.6% on MMLU and 34.6% on GPQA, against 64.2, 28.0%, 65.4% and 29.2% for Chain-of-Thought, and 69.1, 30.6%, 67.6% and 32.9% for the prompt-optimization baseline OPRO. Agents found on MGSM also raised GSM8K accuracy by 25.9% and GSM-Hard by 13.2% over the baselines when moved there. One search run cost about $300 to $500 in API calls, most of it spent evaluating candidate agents.

AFlow

AFlow is a workflow search that writes an agentic workflow as code and improves it with Monte Carlo Tree Search. It takes a dataset, an evaluator, and a set of operators, and returns the best workflow found.

A workflow is a graph of model calls. Nodes are calls with a prompt; edges are the code that connects them. To keep the search tractable, the model, temperature, and output format are fixed, and common patterns are packaged as operators: Generate, Format, Review and Revise, Ensemble, Test, Programmer, and a plain Custom node. The optimizer therefore mostly edits prompts and the code between nodes.

The search starts from a blank template. Each round, it selects a workflow from the tree, mixing a uniform draw with a score-weighted draw over the top few and always keeping the blank template as an option, asks the optimizer model (Claude 3.5 Sonnet) to modify it given what the tree has recorded about past attempts, runs the new workflow on the validation set several times, and writes the score and the change back into the tree. The paper uses 20 rounds. The validation set is the problems on which the blank workflow’s score varied most across five runs.

In the paper’s results, with GPT-4o-mini running the workflows, AFlow averaged 80.3% across HotpotQA, DROP, HumanEval, MBPP, GSM8K, and a hard MATH subset, compared with 76.0% for the best hand-designed method (self-consistency Chain-of-Thought) and 67.2% for ADAS. On HumanEval, it scored 94.7% against 87.0% for calling the model directly. The paper also reports that its workflows let smaller models beat GPT-4o on some tasks at 4.55% of its cost. These are the paper’s own runs, on an 80% test split of each benchmark, averaged over three runs.

Evolving code on general coding tasks

The evolutionary pipelines above are only run on problems with a score to climb. A few systems evolve code on ordinary coding tasks instead, using tests as the score. None of them report evolving a whole app or repository.

SE-Agent

SE-Agent evolves whole solving attempts for a GitHub issue. For each issue, it keeps a pool of up to 10 agent trajectories. Each round it revises trajectories, recombines segments from different ones (an explicit crossover), restructures them, and keeps the best few with some diversity, until the reward stops improving. The patch from the best trajectory is the output.

On SWE-bench Verified, SE-Agent with Claude 3.7 Sonnet resolved 61.2% of issues, against 40.6% for SWE-agent and 47.4% for SWE-Search, a tree search over the same agent. With DeepSeek-V3, it scored 54.8% against 31.6% and 39.4%. These are pass@1 numbers from the paper’s own runs. Single-pass agents on newer models score above 75% on the same benchmark (Live-SWE-agent reports 77.4% with Gemini 3 Pro), so the gain is over the same model, not over the leaderboard.

Satori-SWE

Satori-SWE evolves patches instead of trajectories, with a small model. It is an Agentless-style pipeline: retrieve the files, then edit. It samples 25 patches, selects, and asks the model to mutate them in the next round. The model is trained by RL so that each round’s patches score higher than the last, so no verifier is needed inside the loop. Tests and a reward model pick the final patch from the pool.

With a 32B model (Qwen2.5-Coder-32B-Instruct), it resolved 41.6% of SWE-bench Verified with a pool of 50 patches, up from 35.8% greedy. That matches models over 100B in the same pipeline: Agentless with DeepSeek-V3 scored 42.0% and with Claude 3.5 Sonnet 50.8%; SWE-agent with Claude 3.7 Sonnet scored 58.2%. The point is sample efficiency at small size, not the top score.

BACE

BACE co-evolves programs and tests for a single problem. It keeps 10 to 15 candidate programs and 20 candidate tests for 10 generations. The model is the only variation operator: for programs it crosses two solutions, debugs, or re-implements; for tests it writes discriminating, complementary, and edge-case tests. Selection uses a belief about which programs are correct, updated from which tests they pass.

On 80 LiveCodeBench v6 problems released after March 2025, BACE with GPT-5-mini reached 66.7% pass@1, against 45.0% for the model called directly and 64.2% for CodeSIM, the best agent baseline. With Qwen2.5-Coder-7B, it scored 29.6% against 11.3% direct. These are a subset, so they are not comparable with the full-set LiveCodeBench numbers below.

EvolRepair

EvolRepair is program repair as a genetic algorithm with the model as every operator. It starts with 6 candidate fixes, groups them by how they behave on the tests, crosses candidates within and across groups, mutates, and runs up to 5 turns.

On 326 nearly correct programs built from LiveCodeBench problems, it reached 96.6% pass@1 with DeepSeek V3.1, against 94.5% for REx and 93.3% for ChatRepair, and 43.3% with Llama 3.3 70B against 38.3% and 34.4%. The gains are a few points over the best repair baselines, and the test set is the authors’ own.

ARJA-CLM

ARJA-CLM is the older genetic-programming repair line with a code model inside. ARJA keeps a population of 40 edit vectors over suspicious statements, crosses and mutates them for 50 generations, and scores them on the tests. The model (CodeLlama-7B) fills in masked lines to supply the candidate code that the operators choose from.

On 224 Defects4J bugs, it correctly fixed 56 (94 plausible), against 34 for ARJA-e, 41 for HERCULES, and 55 for GAMMA, and it was the best entrant at the APR 2024 competition with 7 correct fixes. These are Java bugs with the faulty lines given.

EvoGit

EvoGit is the one attempt to evolve a whole codebase. 16 coding agents work on one repository as a git phylogenetic tree: parents are frontier commits, a mutation is one small edit in a random 128-line region, a child is kept only if build, lint, type, and test checks do not regress and a model judge approves, and crossover is a git merge from the common ancestor. A human prunes the frontier every 10 to 20 iterations, for up to 120 iterations.

The paper shows two case studies: a Next.js single-page promotional website built from scratch, and a self-evolving bin-packing solver. There are no benchmark numbers, only the artifacts. So app-scale evolution has been tried once, and only qualitatively.

Benchmark literature

I used Claude to gather much of the benchmark literature and built a small clustering algorithm to help me study the 474 benchmarks related to “code generation”.

Several interesting benchmarks are highly relevant to our problem.[7]

This week, I focused on general code generation benchmarks.

AlphaEvolve math repository

This benchmark contains 67 mathematical problems (analysis, combinatorics, geometry, number theory), each recast as optimizing a score of an explicit construction, on which the AlphaEvolve evolutionary coding agent was run to match or beat best-known bounds.

It comes with the problem prompt, the evaluator, the initial program, and evolved programs.

It measures whether the generated code can find good mathematical constructions, such as a packing of circles or a tiling of a grid. In search mode, the program searches for a good construction at a fixed problem size.

In generalizer mode, it tries to find one rule or algorithm that takes the problem size n and builds a construction for that size, rather than finding a separate answer for each n. For example, a program might take n and return a tiling of an n × n grid. It is scored across a range of sizes; this does not by itself prove that the rule works, or is optimal, for every n.

The repository’s current results list 19 new records and 4 earlier records that have since been improved by others. AlphaEvolve also matched known optimal solutions on 12 problems. These are improvements to mathematical constructions, not a percentage of coding tasks passed.

CodeAssay

It is a benchmark of 185 Python tasks across 10 software-engineering categories, including algorithms, text processing, file I/O, networking, databases, and concurrency, scored by hidden unit tests.

It measures code-generating LLMs’ ability to solve small, self-contained programming tasks. For correct solutions, it also compares code style, cyclomatic complexity, and static-analysis findings[8].

The input is a natural-language task description, a signature, and public tests. The model must write the implementation. If it fails the public tests, it gets one chance to repair the code using the failure report. The final code is scored on separate hidden tests that the model never sees.

In the paper’s results, GPT-5.6-sol and Claude Sonnet 5 each solved 183 of 185 tasks (98.9%), while Claude Haiku 4.5 scored 96.8% and Claude Sonnet 4.5 scored 95.1%. These are final scores after at most one repair.

Aider Polyglot

A benchmark of 225 programming exercises across C++, Go, Java, JavaScript, Python, and Rust. It measures the model’s ability to implement a solution and edit its code using test feedback.

The input is a natural-language exercise description and starter code. The model must edit the files to implement the required behavior. Aider runs the unit tests and, if they fail, gives the model the error output and one chance to repair the code. The score is the percentage of exercises that pass all their tests.

In Aider’s official results, GPT-5 with high reasoning effort solved 198 of 225 exercises (88.0%), up from 52.0% on the first attempt. This run is from August 2025.

A newer MGM paper reports 96.89% with DeepSeek-V4-Pro and 93.3% with Qwen3.6-35B-A3B on the full 225 exercises. MGM uses its own coding agent, developed on 60 of these tasks, with repeated testing and repair.

LiveCodeBench v6

A benchmark of contest-programming problems from LeetCode, AtCoder, and Codeforces. It measures the model’s ability to turn a problem statement into a correct algorithm and implementation. The cumulative v6 release contains 1,055 problems, though evaluations can select smaller date ranges.

The input is the problem statement, examples, and input/output constraints. The model must write a program that runs against public and hidden tests. The code-generation score is pass@1: the estimated percentage of problems solved by one generated solution, with all tests passing.

In DeepSeek’s results, DeepSeek-V4-Pro in Max mode scored 93.5%. Qwen’s newer results report 91.9% for Qwen3.8-Flash-Next and 90.3% for Qwen3.8-27B.

LiveOIBench

A benchmark of 403 recent informatics olympiad problems (2023-2025) with official test suites and scoring rubrics; the model writes a solution in C++ and is scored by pass rate, contest points, human percentile, and derived Codeforces Elo.

The input is the full problem statement in Markdown, with time and memory limits inside a fixed prompt asking for a C++ solution that solves all subtasks. The output C++ code is compiled, run against the official tests, and scored per subtask.

In the paper’s results, GPT-5 solved 63.03% of tasks; GPT-OSS-120B with high reasoning effort solved 60.14%; Gemini 2.5 Pro solved 44.46%; and Claude Sonnet 4.5 solved 27.05%. GPT-5 outperformed 81.76% of human contestants on average. These results use the best of 8 generated solutions per problem.

SpreadsheetBench

A benchmark of 912 real spreadsheet requests, including extracting text, calculating totals, and finding data across sheets. It measures the model’s ability to write code that manipulates spreadsheets, including files with multiple tables, missing headers, and irregular layouts.

The input is a natural-language request and an Excel workbook, including where the answer should go. The model must write code that makes the requested changes and saves the resulting workbook.

The same code is tested on several versions of the workbook with different cell values, about three per request. The benchmark compares the results with reference answers. The benchmark reports both partial credit for passing some cases and a stricter score requiring all cases to pass.

On the benchmark’s full 912-task leaderboard, Qingqiu Agent scored 83.11%, WPS AI (Seed 2.0) scored 73.46%, and Gemini in Google Sheets scored 70.48%.

NL2Repo-Bench

A benchmark of 104 tasks where a coding agent must build a complete Python library from a natural-language specification. It measures the agent’s ability to organize and implement a working code repository.

The input describes the project, its dependencies, the expected directory structure, the required APIs, and examples of their behavior. The agent starts with only this document and must write the files and make the library installable.

The finished repository is run against the original library’s unit tests, which are hidden during development. The benchmark reports the average percentage of tests passed and the number of repositories that pass every test.

In DeepSeek’s newer results, Claude Opus 5 scored 75.3%; DeepSeek-V4.1-Flash scored 64.0%; GLM-5.3 scored 58.0%; and GPT-5.6 Sol scored 56.8%.[9]

Target

After carefully studying the benchmark landscape for this problem, I want to think more about “code generation” itself.

Premise

We want an “oracle” to generate “code”/“target” given our “query”. Before deciding or solidifying what these are, or how they will be, I want to think about their “shape.” By “shape,” I mean thinking about the properties and constraints of all these definitions that make (a sort of) an outline of these definitions.

Query

We constrain this to a single input; the oracle must extract intent and goals from the input and create the code/target without extensive hand-holding from the user. This also means that we don’t allow the oracle to converse with the user.

I still haven’t decided whether we’ll separate class-level or generalizable queries from instance-level queries, or whether the Oracle produces code for the class rather than the instance, regardless of how we query. For example, I could input this query to the Oracle: Scrape my site (https://ddi-droid.github.io/) for my image vs. Scrape a personal website for that person's image; The Oracle could give the same code for both queries or could give a more instance-level code for the first query while generating a general person-image extractor for the second one.[10]

Code and Oracle

There is already a great deal of work on code generation, as the Literature Review and Benchmark Literature sections show. We have models and agent harnesses[11] that can generate programs, modify existing repositories, and build libraries and websites.

Before we model the shape of the code, I would like to think about some questions like: Why generate code to do tasks? When we can have agentic LLM harnesses do it?

Because Code/Programs are static, we can compile useful traits into them, such as being a generic solver for a class of problems and minimizing running time and cost.

These generated codes can be much more efficient and correct while solving a class of tasks than their agentic counterparts.

NeuroSymbolic Programs

Henry Kautz’s six-type taxonomy describes different ways to combine neural and symbolic computation.

  1. Type 1: Symbolic → Neural → Symbolic. A neural model takes symbols as input and returns symbols as output, such as a translation model taking words in one language and producing words in another. There need not be a separate symbolic reasoner.

  2. Type 2: Symbolic[Neural]. A symbolic problem solver calls a neural model as a helper. For example, AlphaGo’s tree search uses neural predictions to guide its search. The search procedure controls the process.

  3. Type 3: Neural | Symbolic. A neural model turns raw input into a symbolic representation, which a symbolic reasoner then uses. For example, perception identifies objects in an image, and a reasoner answers questions about them. Feedback from the reasoning stage can also help train the neural part.

  4. **Type 4: Neuro:Symbolic → Neuro. ** **** Symbolic rules supply training examples, and a neural model learns from them. For example, it learns to simplify mathematical expressions from correct input-output pairs. The trained model predicts answers without necessarily running those rules itself.

  5. Type 5: Neuro_{Symbolic}. Symbolic rules become structures or operations within the neural network, rather than just examples in its training data. Logic Tensor Networks are one example discussed by Kautz.

  6. Type 6: Neural[Symbolic]. The neural system calls a symbolic solver when needed, gives it a problem, and uses the returned result to continue. For example, a neural agent can ask a path-finding algorithm for a route before deciding how to move. This reverses the control relationship in Type 2.
