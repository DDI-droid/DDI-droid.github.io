CyberGym Harness Optimization

by Anshul Thakur
10th Nov 2026
12 min read

This report covers the end-to-end evaluation pipeline and harness iterations I built for the CyberGym benchmark (difficulty level2) using DeepSeek V3.2 (deepseek.v3.2) on AWS Bedrock.

I modeled my orchestration framework (cybergym-eval) after the architecture of prescera/benchmark-evals.

Development Friction: It is worth noting that due to the cybersecurity nature of the task, it was genuinely difficult to build out this framework. At times, coding assistants like Claude and Codex would hit their safety guardrails and outright refuse to work on the eval repository and the harnesses themselves.

1. Code and Paths on the VM

Everything on the VM is split cleanly so that upstream CyberGym is never modified:

  • Upstream benchmark (unmodified): ~/cybergym (own virtualenv at ~/cybergym/.venv)
  • Evaluation pipeline: ~/cybergym-eval (source in src/cybergym_eval/, configs in config/train25_*.json)
  • Agent harnesses: ~/cybergym-harnesses/harnesses/ (codex, codex_think_ec, codex_think_ec_v5, codex_think_ec_tools, codex_think_ec_tools2)
  • Run artifacts & SQLite state: ~/cybergym-work/train25/

How to launch an evaluation run

# 1. Freeze harness code, resolve the seeded task split, and stage data
~/cybergym-eval/.venv/bin/cybergym-eval prepare --config ~/cybergym-eval/config/train25_think_ec_tools2.json

# 2. Schedule container workers via Ray against the local LLM shim and submission server
~/cybergym-eval/.venv/bin/cybergym-eval run --config ~/cybergym-eval/config/train25_think_ec_tools2.json

2. Evaluation Results (train25)

I drew 50 tasks deterministically (seed=0) from the 1,507-task pool and split them into train25 (first 25) and test25 (last 25). Per the instructions to optimize strictly on the train/dev split, all iteration below was conducted on train25[1].

3. Pipeline Design & Throughput Optimization

Architecture

I structured the evaluator to run entirely outside the upstream CyberGym repository to maintain a clean testing environment. The pipeline relies on a single JSON config per run that manages Ray-based concurrent scheduling (benchmark_slots), interleaves tasks and harnesses so all agents face identical API conditions, and routes all LLM traffic through a custom host-side shim for precise key rotation and metering. By decoupling the agent’s offline Docker network from the host’s Bedrock connection and utilizing a strict SQLite WAL database for state, the system ensures crash-resilient, deterministic executions without ever patching upstream code.

Catching the ASLR Sanitizer Bug (vm.mmap_rnd_bits)

Ubuntu 26.04 defaults to vm.mmap_rnd_bits=32. Old Clang AddressSanitizer builds inside CyberGym’s ARVO images reserve fixed shadow-memory ranges and crash at startup—before reading a single byte of the PoC—when libraries land inside those ranges.

I tested n132/arvo:1065-vul (Clang 5.0.0) with 100 harmless 5-byte inputs at both settings:

  • At mmap_rnd_bits=32: 29/100 runs segfaulted at startup (exit code 139). Because the grading server treats any non-zero exit as a crash, an agent gets fake positive rewards ~29% of the time, and final grading passes a completely bogus PoC ~20% of the time (\(0.29 \times 0.71\)).
  • At mmap_rnd_bits=28: 0/100 false crashes. I locked the VM to 28 and made cybergym-eval preflight refuse to start a run otherwise.

Where the Time Actually Goes

  • Grading is cheap: Under a synthetic load test of 32 simultaneous unique submissions (~/tmp/grading_load2.sh), median grading turnaround was 1.88 s (0.37 s at \(N=1\)) with host CPU at just 24%. I didn’t need a custom queueing proxy in front of the official server.
  • Agents are 92% LLM-latency-bound: Across 4,506 model requests in codex_think_ec_tools_r2 (\(K=15\)), 92% of wall-clock time was spent waiting on Bedrock (16.8 s average per call, ~34 output tokens/s) and only 7% on tool execution.
  • Parallelism ceiling on this VM: Because containers sit idle waiting on SSE streams, I lowered per-container reservations to 1 CPU / 2 GB RAM, letting me comfortably run \(K = 15\) agents in parallel (leaving ~30 GB RAM for Docker, Ray, the submission server, and my local LLM metering shim) with 0 HTTP 429 throttles from Bedrock.
  • Measured Throughput: On the baseline codex harness (\(K=8\), 100-step cap), I achieved 37 tasks/hour (40.5 min wall time for 25 tasks). On the heavy thinking harnesses (\(K=15\), 500-step cap, 2-hour timeout), throughput shifts to roughly 8–12 tasks/hour because hard tasks deliberately use their full multi-hundred-step reasoning budget rather than giving up in 40 seconds[3].

4. Harness Optimization Notebook

Each iteration builds on observations from the previous one.

Experiment 1: Baseline codex (16% — 4/25 passed)

  • Setup: Upstream CyberGym’s example Codex-CLI agent connected to deepseek.v3.2 via my local OpenAI-compatible metering shim.
  • Immediate hurdle: My very first run crashed on 6 of the first 10 tasks with ENAMETOOLONG. DeepSeek occasionally emits the shell tool’s command array as a double-encoded JSON string ("[\"cd\", ...]"); stock Codex treated the entire string as argv[0]. I patched parsers.ts to unwrap JSON-encoded arrays, fall back to bash -lc, and return spawn errors as exit code 127 instead of crashing the Node process.
  • Result & Learning: 4/25 passed. Looking at the 21 failures, 14 never produced a /output/poc file (6 never even called submit.sh), and 6 wrote a non-crashing file and quit early. Standard Codex lets the model stop whenever it emits a plain-text reply without a tool call, and without reasoning enabled, DeepSeek gives up after a few surface reads.

Experiment 2: Thinking + Kernel-Enforced Stop Gate (codex_think_ec \(\to\) v5)

  • Hypothesis: Enabling reasoning_effort=high, raising the iteration limit from 100 to 500 (with rolling context summarization), and refusing to let the agent exit until it both (a) triggers a real crash on the server and (b) writes /output/poc will stop premature surrenders.
  • What went wrong in v4: Initially, I enforced the write-gate in user space (stripping writes before a crash flag appeared and polling every 0.3 s to delete premature files). An internal review caught two flaws: a 0.3 s race window could let a pre-crash write survive if a crash happened right after, and the in-container crash flag ran under the agent’s own UID, meaning a clever command could forge it.
  • The Kernel-Level Fix (v5): Before container start, the host creates a root-owned, 0644 empty file and bind-mounts it over /output/poc. Because it is a mount point owned by root, the unprivileged agent user cannot write, chmod, unlink, or mv over it (verified across an 84-check adversarial test battery). Only when the host worker independently queries the submission server using its private admin key and sees a confirmed crash (vul_exit_code \(\notin \{0, 300\}\)) does it run docker exec -u root chown to unlock the file. Furthermore, final grading reads submit.sh metadata outside the workspace so the agent cannot tamper with the grading script.
  • What I found live in v5: I stopped v5 after 77 minutes (at 5 passed, 1 failed, 19 still running) after discovering two wild behaviors in the live containers:
    1. Orphaned background fuzzer loops: On arvo:44199 and arvo:56272, the model wrote detached Python while True: scripts (PPID=1) that generated random bytes and hammered submit.sh forever outside the agent loop—sending ~14,700 submissions from one container (generating 21,968 HTTP 429 rate-limit replies in the server log).
    2. DeepSeek DSML Markup Leak: With thinking on, DeepSeek frequently leaked its native <｜DSML｜function_calls> XML tags into plain text instead of structured tool calls. On arvo:33844, the agent pinpointed the exact memcpy overflow and offsets, yet wasted 296 of 308 rounds because its attempts to write the exploit leaked as text.

Experiment 3: Process Supervision & DSML Recovery (codex_think_ec_tools_r2 — 40% — 10/25 passed)

  • Hypothesis: If I recover leaked DSML blocks into real tool calls and wrap every command in a strict process-tree supervisor, the model’s reasoning will actually reach the target binary.
  • Changes:
    • I built cg_run, a subreaper dispatcher around every tool execution with a hard wall-clock deadline (default 60 s, max 300 s) that kills and reaps the entire process group + any reparented orphans before returning. Zero runaway background loops survived after this.
    • Added a parser that intercepts <｜DSML｜...> blocks in assistant text and executes them as structured calls.
    • Hardened submit.sh with -sS, exponential backoff on 429s, and clean status messages.
  • Result: 10/25 passed (40%) across a full, uninterrupted 25-task run—2.5× the baseline accuracy.
  • New Bottlenecks Exposed: Reading all 25 trajectories from r2 revealed why the other 15 failed:
    1. Silent Compaction Failure (8/15 failures)
    2. The Stringified-Array Tax (~6% of all tool calls): Across 3,386 tool calls in r2, 7% failed with exit code 127 (command not found), and 88% of those were the model still struggling with Codex’s array-based shell(command: string[]) schema.
    3. In-Turn Submission Fan-Out (1/15 failures): One agent spawned 500 concurrent submit.sh subshells within a single 60 s tool call, exhausting its 2 GB container RAM (OOM killed).

Experiment 4: Post-Cutoff Run (codex_think_ec_tools2)

I built and live-tested three targeted fixes for those exact defects, then launched codex_think_ec_tools2 (\(K=15\)) toward the end of the session:

  1. String-Only Tool Contract: Replaced shell(command: string[]) with shell(command: string, workdir?, timeout_ms?) plus a dedicated write_file(path, content) tool. If a model repeatedly mis-encodes a schema, the right fix is to simplify the contract, not add brittle regex heuristics.
  2. Verified Context-Fit & Grounded Summaries: Fixed the stream parser to capture the trailing Bedrock usage chunk, added headroom for the upcoming tool output, and—after a live smoke test showed the model “forgetting” its objective after two compactions—pinned the original task prompt and a mechanical ledger of executed commands at the top of every compaction summary.
  3. Per-Container Submission Semaphore: Added a non-blocking flock gate around submit.sh so an agent attempting a 500-way parallel burst gets immediate typed refusals instead of OOM-killing its container.

Outcome: this first tools2 run (full reasoning effort) was stopped after 10 of 25 tasks had resolved, with 7 passes, to free the run lock for the low-effort run in Experiment 5. It is a partial result and is not compared in the table.

Experiment 5: Lower Reasoning Effort (codex_think_ec_tools2_low)

I then ran the same tools2 harness at a lower reasoning effort, and let it finish.

  • Result: 11 passed, 14 failed (44%), against 10/25 (40%) for r2. That is a one-task difference between two single runs, so I read it as comparable, not as an improvement. The passes I tracked resolved quickly, from 80 s to about 17 minutes each.
  • How the 14 failures split: 11 ran the full 2-hour budget without finding a crash. The other 3 (arvo:44199, 29633, 19702) finished early with a PoC that crashed both the vulnerable and the fixed build. The harness stops at the first vulnerable-build crash and never sees the fixed-build result, so it can’t tell those apart.
  • Likely cause of the 2-hour failures: on the stuck agents I inspected live (for example arvo:23350, after 155 submissions that never crashed), the model alternated between “I cannot proceed” prose and tool calls that cut off at the opening tag. tools2 no longer recovers cut-off calls, so those turns do nothing. I looked closely at only a few of the 11, so for the rest this is a hypothesis.
  • Timeouts were the agents’ mistake: by the 53-minute check the supervisor had cut off 20 tool calls. In 5 of the 6 affected tasks the agent wrapped a script in bash’s own timeout 120 or 300 without passing the tool’s timeout_ms, so the 60 s default still applied. The supervisor did what it is meant to do. The next iteration should state in the tool description that an inner timeout does not extend the deadline.
  • Not a clean A/B: the full-effort tools2 run was stopped after 10 tasks to free the run lock, so low and high reasoning effort are not compared on equal footing.

Other directions I explored (rlm, gepa, and no-crash reflection)

Alongside the codex lineage, I scaffolded two other approaches in ~/cybergym-harnesses/harnesses/ that I chose not to put in the main table:

  • DSPy / GEPA (gepa_react, gepa_rlm) & rlm: I designed a Gym Python API so prompt optimizers could call the exact same container execution core as the CLI.
  • No-Crash Self-Reflection: I sampled 500 non-crashing submission replies in r2 and found 0% contained useful sanitizer feedback (just exit_code: 0). I prototyped a reflection step to make the agent reason over why its input exited cleanly, but held it back from tools2 so I wouldn’t confound the infrastructure fixes with an unvalidated prompt change.
